# Architectural Decisions

This file records project decisions and rationale so future work does not need the original conversation history.

## 1. Reuse The Existing Guitar Project

Decision: Continue from `/Users/dc/CodexProjects/guitar` rather than starting a new project.

Rationale: This project already contains useful Blender scenes, MIDI/WAV outputs, V2 lesson tests, dashboard code, and Blender bridge code.

## 2. Use `outputs/v3-tests.blend` As Latest Scene Candidate

Decision: Treat `outputs/v3-tests.blend` as the latest known Blender scene candidate unless the user selects another file.

Rationale: It is newer than `outputs/lesson-v2-tests.blend` and `outputs/reference-guitar.blend`, and appears to match the user's memory of the latest scene.

Superseded by decision 22: renders use `outputs/v4-vertical.blend`, built from this scene.

## 3. Use MIDI As The Structured Music Source

Decision: V1 uses MIDI for musical structure.

Rationale: MIDI already contains notes, ticks, PPQ, tempo changes, time signatures, and tracks. This avoids unreliable audio transcription in the first version.

## 4. Use Final WAV As Master Audio

Decision: V1 uses the final WAV for rendered audio.

Rationale: MIDI provides structure, but the WAV is the sound the viewer should hear. Blender syncs visuals to the WAV using seconds-based timing and `audio_offset`.

## 5. Keep Musical Analysis Outside Blender

Decision: Python owns MIDI parsing, musical timing, measure calculation, and guitar mapping. Blender only renders.

Rationale: Blender is better as a visual renderer than as a music-analysis engine. Keeping analysis outside Blender makes the JSON contract testable and keeps renders deterministic.

## 6. Preserve Ticks And Seconds

Decision: Export both tick-based timing and seconds-based timing.

Rationale: Ticks preserve musical structure. Seconds are required for audio and Blender timeline sync.

## 7. Make JSON The Python-To-Blender Contract

Decision: Normalized JSON is the boundary between analysis and rendering.

Rationale: A stable contract lets the analyzer and Blender importer evolve independently while making import bugs easier to isolate.

## 8. Rebuild Song-Specific Data On Import

Decision: Importing a new song rebuilds song-specific measures, notes, tabs, animations, and audio.

Rationale: Song data should never leak from one import to the next. Reusable scene setup should remain intact.

## 9. Freeze V1 Before Advanced Features

Decision: V1 excludes WAV-to-MIDI, velocity interpretation, chord/key/section detection, AI transcription, and advanced guitar techniques.

Rationale: The first milestone is reliable synchronization and rendering. Higher-level musical interpretation can be added after the base pipeline works.

## 10. Add Normalized Export Beside Existing V2

Decision: Add `guitar_video_app/core/normalized_song.py`, `guitar_video_app/core/music_analyzer.py`, and the `normalize-midi` CLI command without replacing the existing V2 lesson renderer.

Rationale: The current V2 dashboard and Blender workflow is already verified. A separate normalized exporter lets the project prove the MIDI-to-JSON contract first, then add compatibility conversion or direct Blender import with lower risk.

## 11. Convert Normalized JSON To V2 Before Direct Blender Import

Decision: Add a normalized-to-V2 compatibility bridge for fixed-tempo, single-time-signature songs before changing Blender import behavior.

Rationale: V2 can already render beat-based lessons reliably, but it cannot represent tempo maps or time-signature changes. The bridge lets MIDI-derived normalized songs use the existing renderer while keeping richer normalized JSON as the long-term contract.

## 12. Dashboard Stores Converted V2 For Normalized Imports

Decision: When the dashboard receives normalized JSON, it converts the file to V2 lesson JSON and stores that converted V2 file for preview and Blender transfer.

Rationale: This keeps the verified dashboard and Blender bridge unchanged while allowing the user to import normalized MIDI-derived song data. Direct normalized Blender import remains the later architecture step.

## 13. Render Videos In Background Blender From The Dashboard

Decision: The dashboard Render button runs `scripts/render_lesson.py` in a separate background Blender process (`Blender -b outputs/v3-tests.blend`) using the Workbench engine, 30 fps, and a 1080x1350 frame (now `outputs/v4-vertical.blend` at 1080x1920, see decision 22). Videos are stored in `data/dashboard/<song>/renders/`, named after the song (`<Song name>.mp4`, test renders `<Song name> (test).mp4`, with characters not allowed in file names replaced and a number added instead of replacing an earlier render). Only one render runs at a time.

Rationale: Rendering an animation from the Blender window crashes, because the lesson frame handler creates objects during the render. A background process avoids this, does not need the Blender window open, and leaves the open scene untouched. Lesson timing stays beat-based, so changing the render fps does not change musical timing.

## 14. Standard Notation Is A Dashboard Display Layer

Decision: The dashboard draws standard notation above the tab preview with VexFlow (vendored in `guitar_video_app/ui/vexflow.min.js`). Notes are snapped to a 16th-note grid for display only, written an octave above sounding pitch, and split into a melody voice (strings 1-3, stems up) and a bass voice (strings 4-6, stems down). No key signature is shown; accidentals use sharps.

Rationale: The lesson JSON and Blender timing stay unquantized and authoritative, so the notation cannot change sync. Key detection is outside V1, so notation uses C with accidentals until a key is part of the song data.

## 15. Re-Time Lessons Without Moving Notes In Time

Decision: The dashboard can re-grid a lesson with a tempo and a first-beat time (`guitar_video_app/core/retime.py`, `POST /api/songs/{id}/timing`). Every note keeps its audio time: beats are recomputed from seconds and the audio offset shifts by the same amount. Notes before the first beat get whole lead-in measures, except notes at most 30 ms early, which move onto the first beat. A suggestion endpoint fits note onsets to a 16th-note grid between 60 and 180 BPM.

Rationale: Audio transcription writes a placeholder 120 BPM, so measures and notation do not match the music even though note times in seconds are correct. Re-timing fixes measures, pages and notation without changing sync. The source MIDI file is left unchanged.

## 16. Import Audio From Links As A WAV Master

Decision: The dashboard can import a song's audio from a YouTube, Instagram or TikTok link (`guitar_video_app/integrations/link_audio.py`, `POST /api/songs/{id}/assets/link`). yt-dlp downloads the audio and a bundled ffmpeg (imageio-ffmpeg) converts it to 16-bit stereo WAV, which is stored exactly like an uploaded WAV. Only those three sites are accepted, playlists are ignored, and posts longer than 20 minutes are skipped.

Rationale: The pipeline keeps a final WAV as the audio authority, so every source ends as a WAV. A host allowlist keeps the downloader from fetching arbitrary URLs.

## 17. Optional Tidy Step For Transcribed Timing

Decision: A dashboard "Tidy notes" action (`tidy_lesson` in `guitar_video_app/core/retime.py`, `POST /api/songs/{id}/tidy`) cleans transcribed lessons on the 16th-note grid of the current tempo: note starts within 45 ms of a 16th move onto it, the same pitch repeated within 80 ms is merged, and each note holds until the next note in its voice (strings 1-3 or 4-6), up to 2 beats. It is opt-in and should run after the tempo is set.

Rationale: Transcription spreads chord notes over a few milliseconds and gives uneven lengths, which makes the tab and notation hard to read. Unlike re-timing, this does move notes in time, so the shift is capped at 45 ms and it runs only when the user asks.

## 18. Song-Level Fingering For MIDI Without String Tracks

Decision: The Guitar Mapper chooses string and fret for the whole song at once (`plan_positions` in `guitar_video_app/core/fingering_solver.py`). Notes starting within 40 ms are fingered as one chord, fretted notes in a chord span at most 4 frets, and a beam search keeps the hand in a 4-fret position when possible, prefers frets up to 7, and avoids reusing a string whose previous note is still ringing. Notes from tracks named "string N" keep that string.

Rationale: Transcribed MIDI almost never starts chord notes on the same tick, so choosing positions per exact-tick group with only the previous group in view jumped around the neck and put open-position music on frets 12-15. The mapper still runs in Python, so Blender only receives the chosen positions.

## 19. Cleaner Transcription And Automatic Timing On Generate MIDI

Decision: Generate MIDI runs Basic Pitch with onset threshold 0.6, frame threshold 0.4 and no melodia note extension (`SETTINGS` in `guitar_video_app/core/audio_transcription.py`). The raw MIDI is then cleaned (`guitar_video_app/core/transcription_cleanup.py`): a note at fret 8+ on the high E that starts with a louder note exactly 1-2 octaves or an octave and a fifth below is dropped as an overtone, and a note that starts where the same pitch just ended while more than 10% quieter is joined onto it as one held note. A quieter note under 0.16 s exactly 1-2 octaves or an octave and a fifth above a note starting within 80 ms is also dropped, as is a short quieter note running straight into a louder note of the same pitch. When a pitch has sounded three times at a steady spacing and Basic Pitch saw an onset (strength 0.4+, saved by `basic_pitch_runner.py` as `.onsets.json`) exactly where the next or previous repeat belongs, that note is restored. After fingering, the dashboard fits tempo and downbeat, re-times and tidies the lesson automatically. Tidy now picks an 8th grid unless over a tenth of notes sit on in-between 16ths, and snaps a note up to 80 ms behind a chord onto that chord, and splits voices into bass (strings 5-6, or a string-4 note held a beat or starting a measure, with no lower note from that measure still sounding) and melody instead of strings 1-3 and 4-6; bass notes may hold a full measure. The notation uses the same bass rule and grid. Imported MIDI files are not cleaned.

Rationale: Measured against a published tab of a fingerstyle recording (`data/benchmarks/passacaglia_reference.json`), the old defaults found 92% of real notes but 44% of detected notes were false (ringing notes detected again, overtones), which pushed fingering up to fret 19. The new chain keeps 93% of real notes with 6% false notes, 91% of matched notes on the same string and fret as the tab, and no fret above 5; repeated-note patterns (bass, moving line, repeated top note) come out the same in every measure. Re-timing keeps every note's audio time; tidy moves starts by at most 45 ms.

## 20. Optional Tempo Changes In Lesson V2

Decision: Lesson V2 JSON may carry `tempo_changes` (`[{"beat": "24", "bpm": 111}]`) after the starting `tempo_bpm`. All beat-to-seconds conversion goes through one tempo map in `guitar_video_app/core/lesson_v2.py` (`tempo_map`, `seconds_at`, `beat_at`), used by Blender playback, MIDI export, the dashboard summary and re-timing; the dashboard preview mirrors it in JavaScript. MIDI imports with real tempo changes now convert to V2 instead of being rejected. Automatic timing on Generate MIDI fits a tempo per measure after the global fit (`fit_tempo_map` in `guitar_video_app/core/retime.py`): a beam search over whole-BPM tempos within 80-125% of the global tempo, where a note costs 1 when it is more than 45 ms off its measure's grid and a tempo change costs 2, so a change only appears when it puts at least two more notes on the grid. Beat 0 and every note's audio time stay put. Afterwards, a pitch that starts on two grid lines up to 2 beats apart gets its next (or previous) repeat restored when Basic Pitch saw an onset of that pitch there (strength 0.4+), unless a note starting there explains it as an overtone (`restore_repeats`). The last bass note rings to its bar line once it lasts half the rest of the measure. Manual "Apply timing" still sets one tempo and drops tempo changes.

Rationale: Players slow down at phrase ends. With one tempo, the benchmark's closing measure drifted up to an 8th late, so every note there was drawn on the wrong beat and tidy could not snap it. With the fitted map (one change, 117.5 to 111 BPM) all 71 reference notes land on their exact beat, up from 59, with one extra note; on a steady 32-measure lesson with ±25 ms random timing the fit adds no tempo change. Keeping the map in Python keeps musical timing out of Blender, which only asks the shared module for seconds and beats.

## 21. Song Title Above The Guitar

Decision: Each dashboard song has a video title and an artist/songwriter line (`title` and `subtitle` columns; a NULL title means "use the song name", an empty one hides it), edited in the Render video panel. Send to Blender and renders pass them to `install_title` (`guitar_video_app/integrations/title_overlay.py`, `scripts/render_lesson.py --title --subtitle`), which places two centered camera-facing text objects (`Lesson_Title` in Georgia, `Lesson_Subtitle` in Georgia Italic, falling back to Blender's font) above the headstock and shrinks a line that would be wider than 88% of the frame. Send to Blender reloads the lesson modules so an open Blender picks up dashboard code changes.

Rationale: The title is video presentation, not lesson data, so it lives with the song rather than in lesson JSON, which Generate MIDI and imports replace.

## 22. Vertical 9:16 Video Replaces 4:5

Decision: Lessons render at 1080x1920 from `outputs/v4-vertical.blend`, which `scripts/make_vertical_scene.py` builds from the 4:5 scene `outputs/v3-tests.blend`: the orthographic camera frames 0.90 world units of height (about 15% closer than the 4:5 guitar) and shifts to keep the headstock in view and the neck above the tab. The white tab panel is a centered card from 11.5% to 88.5% of the width and 21% to 36% of the height, under the neck and in front of the guitar body, and the staff lines are centered from 14% to 86% of the width. Short-video apps draw captions over roughly the bottom 20% and buttons over the right 14%, so the panel sits above the captions and the buttons only cover the card's blank right margin; a full-width panel was also tried, but its white band dominated the frame and hid more of the guitar; an earlier version sat on the bottom edge and was hidden by captions. The resize goes through a camera-aligned parent empty (`App_Tab_Frame_9x16`) above the tab group, so the tilted tab scales along screen axes without shearing. The tab still shows two measures per page. Timing, tab layout code and the title overlay are unchanged; they read positions from the camera view.

Rationale: Short-form platforms show 9:16. Chosen from rendered mockups (`outputs/references_9x16/`, tab placement in `outputs/references_9x16_raised/` and `outputs/references_9x16_layout/`, chosen layout "P"): keeping the 4:5 guitar size left a large empty band and a thin tab, while this framing fills the frame and makes tab numbers larger on a phone. Building the scene with a script keeps the 4:5 scene reusable and the framing repeatable.

## 23. MIDI Download Is Written From The Lesson

Decision: The dashboard MIDI download (`/api/songs/<id>/midi`) is built on request from the song's current lesson JSON by `lesson_midi(data, single_track=True)` in `guitar_video_app/core/lesson_midi.py`: one acoustic-guitar track named after the video title, plus a conductor track with the time signature and the lesson's tempo map, notes on the lesson's beat grid, no pitch bends, and a same-pitch note ending where the next one starts. The file is named `<Song name>.mid`. The raw transcription from Generate MIDI (or an imported MIDI file) is still stored as the source for analysis, and is only served when a song has no lesson. `export_lesson` keeps one track per string for audio rendering.

Rationale: Generate MIDI stored Basic Pitch's output with only note cleanup: its default 120 BPM, starts off the beat, uneven ringing lengths and pitch bends, so it looked messy in notation software even though the lesson had been re-timed, tidied and tempo-fitted. Writing the download from the lesson makes it match the video, including manual timing edits.

## 24. Published Tabs Fitted To The Recording

Decision: A song's lesson can come from a tab file instead of transcription (format in `docs/JSON_SCHEMA.md`, "Tab file"; examples in `data/tabs/`). A tab image or PDF is read by the agent into a tab file, not by software on this machine. `fit_tab` in `guitar_video_app/core/tab_import.py` keeps the tab's strings, frets and beats and fits only time: it lines one of the first notes up with strong Basic Pitch onsets of its pitch over 70-140% of the written tempo, scores the first 24 notes (within 80 ms), refines tempo and start on all notes, then moves every whole beat by the weighted median offset of matched onsets within 1.5 beats (three passes, 200/120/80 ms windows) and writes the fewest tempo changes that stay within 15 ms of every beat. When under half of the first notes are heard it also tries the audio 5 semitones lower to 6 higher and reports a capo-like shift. The lesson's beat 0 is at the returned audio second, so the dashboard offset is its negative. The tab is a reference, not the answer: `adapt_to_audio` then makes the lesson follow what the recording plays, using the Basic Pitch onsets and the cleaned transcription. A tab note keeps its string and fret and is matched to an onset of its pitch within 5/16 beat, strong onsets preferred; it is removed when none is near. A transcribed note the tab lacks is added when it starts with an onset of strength 0.6+ inside the tab's bars; same-pitch onsets under 50 ms apart count as one attack, and a same-pitch attack within 0.9 of a 16th (at most 0.18 s) of another is a re-strike and not added. It is also skipped as an overtone when it is an octave, twelfth or double octave of a note struck from 0.25 s before to 80 ms after it, unless the tab has that pitch within 1.5 s. Attacks linked by gaps of at most 90 ms (strong onsets count as links) over at most 0.3 s are one rolled chord: it sits on the earliest written beat of its tab notes when that is within 70 ms of the roll, otherwise on the 16th (or 8th-note triplet, in beats where the tab has triplets) of its first attack. An added note takes the string the tab uses for that pitch within 8 beats, else the string nearest the hand (bass pitches on strings 4-6). The dashboard's Tab row (`POST /api/songs/<id>/assets/tab`) and `scripts/import_tab.py` use the song's stored onsets, transcribing the audio first when needed, keep the uploaded tab next to the lesson, take the video title and artist from the tab, and report how many tab notes were heard and how many notes were moved, added and removed.

Rationale: Against the published intro tab of a Shape of My Heart recording, the transcribed lesson found 65% of the notes, 40% of its notes were not in the tab, only 20% of the found notes were on the tab's string and fret, and its tempo was doubled. Transcription cannot know which of several fingerings a player used. The fitted tab has the tab's fingering and rhythm by construction, and 64 of 75 tab notes land on a recorded onset, 11 ms off on average; the rest are mostly held bass notes the player never struck again. The fit is unchanged when the tab starts 12.5 s into the audio, when the audio is 2 semitones higher, and when it is buried in 3 minutes of random onsets. The player does not play the published tab exactly: bass notes a 16th before beats 2 and 4, a later rhythm in bars 5 and 7, a broken F#m chord after the last strum, and six tab notes never played. The player also rolls chords, striking the strings up to 0.2 s apart; placing each string on its own 16th split the bar 7 chords, and an overtone filter that ignored the tab dropped the F#3 and the top F#4 of the bar 8 F#m. Adapting moved 5 notes, added 21 and removed 6; 85 of the 90 lesson notes are within 80 ms of a recorded onset of their pitch, and the other 5 are notes of rolled chords struck 0.08-0.21 s after the chord's beat. A tab fitted to a recording that plays it exactly is left unchanged. Beats and ticks still come from the tab's grid; the audio decides how long each beat lasts and which notes sit on it.

## 25. Transcribed Tempo 60-120 BPM And No Empty Leading Bars

Decision: `suggest_grid` scores tempos from 60 to 120 BPM (was 60-180), so a song heard at 160 BPM on 8ths is written at 80 BPM on 16ths. After automatic timing and tidying, `trim_leading_measures` drops whole empty measures before the first note and moves the audio offset by the same number of seconds.

Rationale: The Shape of My Heart recording was written at 160 BPM over 17 bars, with bar 1 empty, while its published tab is at 84 BPM in 8 bars. It now comes out at 81 BPM in 9 bars, with the first note in bar 1. The Passacaglia benchmark is unchanged (117.5 BPM, 93% of real notes found, 92% of lesson notes real). The beat phase is still chosen by where most notes land, so a syncopated song can have its bar lines half a beat off; fix it with First beat, or import a tab.

## 26. Per-Song Hand Position

Decision: Each song has an optional hand position (`hand_position` column: the preferred index-finger fret, one of 3, 5, 7, 9 or 12; NULL is automatic). With one set, `plan_positions` scores fretted notes by distance from that fret and 2 per fret outside frets position..position+3, and open strings cost 0.6 from the 3rd fret up, instead of preferring low frets. The dashboard's Hand position selector re-fingers the current lesson (`refinger_lesson` in `guitar_video_app/core/lesson_fingering.py`, `POST /api/songs/<id>/fingering`), keeping every pitch and its timing, and later Generate MIDI runs use the same setting. Importing a tab clears it, because the tab brings its own fingering.

Rationale: The automatic choice prefers low frets and open strings (decision 18), which suits open-position pieces but not songs played higher on the neck. On the transcribed Shape of My Heart lesson, the 3rd fret put 72% of found notes on the published tab's string and fret, up from 20%; the 5th and 7th gave 54% and 50%. Automatic mode re-plans every note to the same place as before, so existing lessons do not change unless a position is chosen.

## 27. Per-Song Guitar Style Applied At Load Time

Decision: Each song has a guitar style (`guitar_style` column; NULL is `natural`), chosen with the Guitar style buttons in the dashboard's Render video section (`POST /api/songs/<id>/style`). `install_style` in `guitar_video_app/integrations/guitar_style.py` applies it whenever a lesson is sent to Blender (`dashboard_sync`) or rendered (`scripts/render_lesson.py --style`). `natural` is the scene as saved: the spruce top and mahogany back, sides, neck and headstock keep their colors and the studio backdrop is shown. `white`, `red` (cherry) and `blue` color only the body: the top, back and sides share one `Guitar | style body` material with the mahogany's roughness, while the neck, headstock and fretboard stay as saved; white and blue keep the studio backdrop and red uses the grey gradient, each chosen from reference renders on both backgrounds. `black` sets both materials to gloss black, hides the backdrop in renders and in the Blender window, and adds a radial grey gradient (display grey 0.42 at the center, 0.2 at the edges): a disc of 48 rings, each with its own flat grey material, parented to the camera just in front of the backdrop and sized to the camera frame. The ring materials are rough and fully metallic, so Workbench returns a fixed share (0.615) of their color with no specular floor, and their greys are exact at the dashboard's render exposure of 0.8. `natural` removes the disc and gives the body parts their own materials back. The `.blend` files are not changed; changing the style raises the song's revision so the dashboard shows Blender as out of date.

Rationale: Workbench renders use each material's viewport display color and one flat color per object, so a style is a set of display colors and a gradient has to be built from flat-colored pieces. A compositor gradient was tried first; it matched in renders but the Blender window cannot show it (the viewport compositor does not run in Solid view), while the ring disc shows in both and matches the compositor reference within one level out of 255 with no visible banding. A black guitar on the existing dark warm-grey backdrop had little contrast; the soft gradient was chosen from reference renders in `outputs/references_style/` over a lighter one because it keeps the off-white title readable. Restoring `natural` returns the materials, backdrop, film and compositor to exactly the saved scene, so existing songs render as before.

## 28. A Reference Tab Reviews An Existing Lesson

Decision: Importing a tab file for a song that already has a lesson (usually from Generate MIDI) reviews that lesson instead of replacing it (`review_with_tab` in `guitar_video_app/core/tab_review.py`, same Tab row and `scripts/import_tab.py`). `find_places` fits the tab to the audio as in decision 24, then searches again without the onsets between the first and last tab note of each place found; a further place counts when at least half of the tab's notes, and 60% of the best place's share, are heard there and its notes overlap no earlier place's by more than a beat (a weak match masks its first measure and the search retries, up to 3 times). Each place is adapted to the playing with `adapt_to_audio`, and its notes replace the lesson's notes starting from 70 ms before the place to 70 ms before its end. Bar lines and tempo follow the tab's fitted beats in those places; before the first place and after the last, measures continue from the tab's tempo with per-measure tempos fitted to the lesson's notes (`fit_tempo_map`, run backwards before the first place); between two places the gap becomes whole measures, fitted the same way and scaled to end where the next place starts. The whole-beat times become one tempo map (`_tempo_changes`, within 15 ms). Lesson notes outside the places keep their audio times, are tidied on the new grid and re-fingered around the tab's notes, which stay fixed: the planner uses the hand position whose fingering of the tab's own notes matches the tab best, when it matches at least 25% of those notes more than the automatic low-fret choice, and otherwise the automatic choice. The previous lesson, offset, hand position and titles are kept (`previous_state` column) so Undo review can restore them while the review report is current; note edits and deletions keep the report, while timing, tidy, fingering and new imports end it. The report pairs old and new notes of the same pitch, closest first: within 80 ms they are unchanged or re-fingered, within 0.3 s moved, otherwise added or removed. The dashboard highlights those changes in the tab preview (removed notes as faint struck-out numbers) with a Show changes toggle. `adapt_to_audio` now adds played notes only when their attack falls inside the tab's bars.

Rationale: Generate MIDI finds most notes but cannot know the player's fingering, and a published tab usually covers one section, so replacing the lesson with the tab lost the rest of the song. Tested on the Shape of My Heart recording with the intro tab cut to bars 1-2 and 1-4, and on that recording joined to itself (bars 1-2 of the tab are played four times): every place was found; in the tab's bars all 45 notes of the full published tab are present on its string and fret with no extra notes, against 35 found and 2 on the tab's string before; in bars the tab does not cover, 20-23 of 27 matched notes are on the published string and fret, up from 15, while pitches and audio times are unchanged. With the full tab, the second copy in the joined recording is found too. On the Passacaglia benchmark, a two- or four-bar excerpt is in open position, so the automatic fingering is kept (41 of 45 and 28 of 29 matched notes on the reference string outside the excerpt, against 43 of 46 and 29 of 29 before); choosing the best hand position without the margin halved that. Preferring the tab's string for each pitch was tried and made no difference or was worse. Before the fix, notes played after a tab's last bar were pulled onto its last 16th, which put a false six-note chord at the end of every section tab. A "notes heard" percentage was left out of the report because rolled chord notes placed on the written beat count as unheard, so it fell even when the lesson improved.

## 29. Fast Tabs Keep Their Written Meter

Decision: A tab written above 120 BPM is fitted, adapted and reviewed counting beats half as fast (quarter = 164 in 2/2 is fitted as 82 counting half notes; doubled again above 240), then written back in the tab's own beats, tempo and time signature (`counted_beat`, `scale_beats` and `import_tab_to_audio` in `guitar_video_app/core/tab_import.py`; `review_with_tab` does the same). Every note keeps its time in seconds and each measure keeps its notes; only the beat-length windows of decision 24 (warping within 1.5 beats, matching within 5/16 beat, the 16th grid, re-strikes, added note lengths) now span the same seconds as for a tab written at 60-120 BPM. Slower tabs are unchanged.

Rationale: The Shape of My Heart intro from a Songsterr-style tab (2/2, quarter = 164, 16 bars) heard 45 of its 73 notes and the adapting step removed 26 of them, while the same music written as 4/4 at 82 heard 62 and removed 5: at twice the written tempo each beat window was half as long in seconds. With counted beats the 2/2 tab gives exactly the 4/4 result (62 of 73 heard; 5 moved, 16 added, 5 removed) and stays in 2/2 over 16 bars, matching the tab's bar numbers. The Passacaglia and 84 BPM Shape of My Heart checks of decisions 24 and 28 give the same results as before.

## 30. Tab Notes Are Moved, Added And Nudged In The Dashboard

Decision: In the dashboard's tab preview a note can be dragged to another time and string, a double-click on an empty spot adds a note (type the fret, Enter), and the note editor has String, Fret, Bar, Beat (quarter-note beat in the bar, from 1) and Length (16th to whole). Dragging snaps to 16ths (Shift: free, stored to 1/48 beat) within the two measures shown; dragging or arrow keys to another string keep the pitch and recompute the fret, and refuse a string that cannot play it or already has a note at that beat. Arrow keys nudge the selected note (left/right a 16th, Shift a beat; up/down to the next string that can play it), Delete removes it, Escape deselects. The server takes `PATCH /api/songs/<id>/notes` with optional `start_beat` and `duration_beats`, `POST` to add (new ids `e001`, `e002`, ...) and `PUT` with a whole note list and lesson end; every edit is validated with `prepare`, moves the lesson end to the bar line after a note that now ends past it, keeps the tab import and review details of the summary, and marks Blender out of date. Undo / Redo (buttons, ⌘Z and ⇧⌘Z) keep note-list snapshots in the page and restore them with `PUT`; the history is cleared whenever the song is reloaded by another action (timing, tidy, fingering, imports), because those change beats. Note edits reload only the lesson, so playback and the shown measures stay.

Rationale: Only string and fret could be edited, so a note on the wrong beat or a note the transcription missed could not be fixed without editing the JSON. Keeping the pitch when changing strings matches how fingering is corrected; changing the pitch stays possible by typing a fret. Tested on a copy of the reviewed Shape of My Heart lesson: drag, arrow keys, add, delete, a clash on the same string and an unplayable string all behave as described, and undoing every edit restores the lesson file exactly.

## 31. Music And Instruments Are Separate

Decision: Musical logic lives in `guitar_video_app/music/` (tempo maps, timing validation, MIDI analysis, transcription cleanup, retiming and tidying, fitting a written part to the audio, the review timeline, MIDI export) and works on notes with a MIDI pitch and beats only; nothing in `music/` imports an instrument. Each instrument is a package under `guitar_video_app/instruments/` implementing the `Instrument` interface in `instruments/base.py` (new part, rules, playable, assign, check, sync, view) and registered in `INSTRUMENTS`; guitar is `instruments/guitar/` (tuning, mapper, fingering planner, hand positions, tab reading and review, the V2 view). Where music code needs an instrument's judgement it asks a `PitchRules` object (`music/rules.py`): which slot a note occupies (notes in one slot cut each other off; the guitar's string, otherwise the pitch), note order, what counts as bass, and whether an added note can be placed. With no part the pitch-only defaults apply. Dashboard lessons are stored as Lesson V3 (`docs/JSON_SCHEMA.md`): `music` plus `parts` keyed by name, the guitar part holding tuning and a string and fret for each note id. Existing V2 files are converted when read and written as V3 on their next save; positions for removed notes are pruned on every write. Blender, the renderer and the dashboard tab editor keep reading V2, which is now the guitar view built from the V3 lesson (`guitar_view`, written to `guitar_view.json` on send and render; `GET .../lesson?part=guitar`); the lesson download is V3. Notes the guitar cannot play are dropped from the music at tolerant MIDI import, as before. The old `guitar_video_app/core/` modules remain as one-line re-exports so older scripts and saved `.blend` startup code keep working.

Rationale: Timing, retiming, fitting and review were written against string and fret, so adding piano would have meant copying or rewriting them. Separating the music from how an instrument plays it lets a new instrument add a package and a part without touching the timing code, and one lesson can later carry several parts over the same notes. Keeping V2 as the Blender contract left the scene, controller and saved `.blend` files unchanged. Before the change, 26 reference outputs were recorded (MIDI and tab imports, retime and tidy, review of the Shape of My Heart lesson, MIDI export, every dashboard endpoint on a copy of the song store, the lesson sent to Blender); afterwards all 26 are identical, the verify scripts give the same results as before, and a test render from a V3 lesson draws the same tab. `scripts/verify_music_without_instrument.py` checks that `music/` imports no instrument and runs analysis, retiming, tidying, fitting, review and MIDI export on a lesson with no parts.

## 32. Piano: Hands From MIDI Tracks Or Planned, Keys Pressed In A Procedural Scene

Decision: Piano is `guitar_video_app/instruments/piano/`. A piano has one key per pitch, so its part stores who plays each note, not where: a hand per note id (`docs/JSON_SCHEMA.md`, piano part), with room for finger numbers and pedal later. Hands come from the MIDI file when it has exactly two note tracks (or channels) that look like hands: track names (left, LH, bass / right, RH, treble, melody) decide which is which, otherwise the higher track is the right hand and the two must be at least 3 semitones apart on average, and at least 90% of each track's chords must fit one hand (5 notes, 16 semitones). Otherwise `plan_hands` chooses the cheapest hands for the whole song (a Viterbi search over chords starting within 40 ms): each hand has a position that moves 1 per semitone, reaches 6 semitones either side, pays for stretches past an octave and more than 5 notes (held notes count half), crossing hands costs extra, and a light pull keeps the left hand low and the right hand high around middle C. Hands chosen in the dashboard (`by: "user"`) or read from tracks (`by: "midi"`) are fixed when planning again. The first part of a lesson is the active one (checked, drawn, exported); a song has an instrument (dashboard `instrument` column, empty for guitar) and switching instrument makes that part active, planning it only if it does not play every note, so switching back finds the earlier fingering or hands. Blender reads a piano view with each note's key, x position in millimetres and hand. The piano scene `outputs/piano-vertical.blend` is built by code from real key dimensions (white keys 23.5 mm, octave 164.5 mm, 150 mm white and 95 mm black key length, 10 mm key dip) instead of a modelled asset, so the keys, their names and their pivots match the view exactly and can later be reused in a larger 3D world. Keys press by rotating about a pivot 400 mm back and switch to the hand's color (right orange, left blue) while more than 35% down; a key starts down 35 ms before its note and rises over 70 ms, and a key struck again lifts first. The camera is orthographic from 55° above the front, framing the keys the song uses (at least 15 white keys, one key of margin) at 40% of the frame height, fixed for the whole song. The dashboard previews a piano song as a piano roll colored by hand; clicking a note flips its hand, and Plan hands plans the rest again. MIDI download writes a right-hand and a left-hand track.

Rationale: What a piano lesson has to show is which hand plays which keys, so the part is a hand per note and the music layer, timing tools and MIDI export stay shared with the guitar (decision 31). Two-hand MIDI files already say which hand plays what; the planner covers single-track MIDI and transcriptions, and flipping a note and planning again corrects its mistakes without undoing the user's choices. On a 16-bar test piece whose hands share the middle of the keyboard, hands from tracks are all correct, and the planner on the same notes merged into one track gets 171 of 184 right (93%); the misses are notes a pianist could take with either hand. A procedural keyboard costs nothing to change, is exact to the millimetre and stays light for Workbench renders; a 38 s test video renders in under a minute. The 26 guitar reference outputs of decision 31 are unchanged, and guitar sends omit the new `instrument` field so the guitar Blender path is untouched. `scripts/verify_piano.py` checks the keyboard geometry, hands from tracks, planner accuracy, retiming, tidying and export of a piano lesson, and the dashboard flow (switch to piano, import, flip, plan, send, two-hand MIDI, switch to guitar and back).

## 33. Sustain Pedal Events Stay Separate From Note Timing

Decision: The MIDI analyzer extracts sustain pedal spans from CC64 into normalized `pedal_events`, and normalized-to-lesson conversion carries them into `music.pedal_events`. The piano view exposes the same optional events for later renderer use, but the current key-press animation still uses physical note start and end times.

Rationale: For piano, key release and sound sustain are different musical facts. Keeping pedal data separate lets Blender later animate the pedal and show sustained sound without changing the note timing contract or disturbing the guitar pipeline.

## 34. PIANO_VISUAL Is A Separate Compact Stage Piano For Visualizations

Decision: A second piano asset, PIANO_VISUAL, is built procedurally by `guitar_video_app/integrations/piano_visual.py` into `outputs/piano-visual.blend` (`scripts/make_piano_visual_scene.py`). It is a slim black 88-key stage piano on two side legs with a rear stretcher, with no lid, music stand, screen or speakers, and nothing within the keyboard's footprint above the black key tops: the body behind the keys is 28 mm above the white keys and holds only flush controls. Keys are `PianoVisual_Key_<000-087>_<note>` (A0 = MIDI 21 = index 000, C4 = 60 = 039, C8 = 108 = 087; sharps are written `s`, for example `As0`) with `midi_number`, `note_name`, `key_index`, `key_type`, `press_angle`, `pv_highlight` and `pv_highlight_color`. Each key's origin is its pivot, 250 mm behind the front edge at the bottom of the white keys; `rotation_euler.x = press_angle` dips a white key's front by 10 mm, and 0 is rest. White keys are notched around the black keys. The key materials glow by the key's own `pv_highlight`, so highlighting needs no material swaps. Empties give the keyboard center, its ends, a camera target and, per key, a top center and a particle spawn point 15 mm above it; they do not move with key presses. A floor-standing unit of three pedals sits between the legs, joined to the stretcher: `PianoVisual_Pedal_Soft`, `_Sostenuto` and `_Sustain` (left to right, `midi_cc` 67, 66, 64). Each has `pedal_type`, `press_angle` and the same highlight properties as the keys, with its origin at its rear hinge. `rotation_euler.x = press_angle` pushes the tip down 14 mm, the same hinge-and-rotate approach as the grand piano's sustain pedal. Key x positions come from `instruments/piano/keyboard.py`, the same layout as the lesson piano, so `x_mm` and MIDI numbers in the piano view map directly onto it. It is not yet driven by lessons, and the lesson piano (`piano_scene.py`, `piano_lesson.py`) is unchanged.

Rationale: The grand piano body fills the space above and behind the keys that falling notes and particles need. A separate asset keeps the lesson piano working while the visualization piano grows. Building it from code keeps names, MIDI mapping and dimensions exact. Bevels are applied, so key presses move plain meshes, and the asset is about 18,000 triangles, which is light enough for an 8 GB M1. `scripts/verify_piano_visual.py` checks the 88 keys, MIDI 21-108, 52 white and 36 black keys, unique names, that there is no baked animation, that each key presses without moving any other key or anchor, and that a vertical ray from every key is clear.

## 35. PIANO_VISUAL Particles Are Stateless Geometry Nodes Driven By Performance Seconds

Decision: `guitar_video_app/integrations/piano_visual_particles.py` plays a piano view on PIANO_VISUAL. Note starts, releases and pedal-sustained ends in seconds come from `instruments/piano/performance.py` (the lesson's tempo map), and key presses reuse the lesson piano's press and release envelope (`piano_lesson.key_events`), so Blender does no musical analysis and the JSON format is unchanged. A helper object `PianoVisual_Plumes`, in its own collection outside the asset, has one point per note at its key's spawn anchor. Its Geometry Nodes modifier computes every particle from the scene time: each sounding note gets 924 slots, and a slot emits at a fixed period (420 particles per second while the key is held), so a particle lives 2.2 s and its position, size and glow are pure functions of its age. Particles rise about 0.3 m/s, swirl with 4D noise and spread wider as they age. A quarter of them are sparks that break away and twinkle after 40% of their life, and a third are larger, fainter, see-through mist that gives the plume body. They are drawn as small squares turned to the active camera with a round glow painted on them, in blue shading from white-blue at birth to deep blue. On release, emission stops and the plume floats up and fades. While the sustain pedal alone holds the note, 40% of the slots keep emitting, smaller and 55% dimmer. Held keys glow blue through `pv_highlight`, pedal-held keys glow at 30%, and the sustain pedal presses by `pedal_amount`. A compositor bloom (threshold 2) is added unless the scene already composites. `scripts/render_piano_visual.py` opens `outputs/piano-visual.blend`, loads the view and the final WAV, sets the frame range from the tempo map plus the last plume's fade, and renders a video or stills. It never saves the `.blend`. The dashboard does not send to PIANO_VISUAL yet.

Rationale: Stateless particles need no simulation, bake or cache, render any frame the same in any order, and stay locked to the WAV because every time is in seconds from the tempo map. A particle system or a simulation zone would have to play from the start and store frames. On Blender 5.2 EEVEE the point cloud's own point shapes read as hard diamonds up close, so camera-facing sprites with a painted glow are used; about 3,400 sprites are live at the busiest moment of a 12 s test phrase, a frame evaluates in about 16 ms and renders in under a second at half size on an M1 with 8 GB. `scripts/verify_piano_visual_particles.py` checks that there are no particles before the first note, emission rate and position over the key, that a released key stops emitting and its plume rises and clears within a lifetime, that pedal-held emission is thinner and stops when the pedal lifts, that seeking back to a frame gives identical particles, key, glow and pedal motion, the particle budget, and that the asset, its animation and the `.blend` on disk are unchanged.

## 36. A Piano Song Chooses Its Piano Look In The Dashboard

Decision: Each dashboard song has a piano look (`piano_look` column; NULL is the lesson keyboard, `visual` is the PIANO_VISUAL particle stage), chosen with the Piano look buttons in the Render video section of piano songs (`POST /api/songs/<id>/piano-look`). Changing it raises the song's revision, as the guitar style does. Guitar songs ignore it. Send to Blender adds `piano_look: "visual"` to the `dashboard_sync` command. The bridge (`dashboard_bridge.sync_piano`) then requires `outputs/piano-visual.blend` to be open, loads the view with `piano_visual_particles.install` and the WAV at the song's offset, and on failure restores the previous lesson, or clears the plumes when there was none. Without it, it requires `outputs/piano-vertical.blend` as before. The bridge reloads the PIANO_VISUAL modules so an open Blender picks up code changes. Renders of particle-stage songs run `scripts/render_piano_visual.py` on `outputs/piano-visual.blend`. Test 4 s is a draft at half size and 32 samples. Render full renders the whole song at full size (1080x1920, as short-video platforms expect) and also at 32 samples, which looks as clean as the scene's 64 for these glowing notes and takes about half the time. Render full is full quality with no end frame, so it runs to the end of the last plume, and the script prints `Frame range: <start>-<end>` so the dashboard's progress bar uses that range. The particle stage shows no title, so the title fields are hidden for it.

Rationale: The lesson keyboard and the particle stage suit different videos, so the look belongs to the song, like the guitar style. Sending to the wrong open scene fails with a message naming the right file instead of loading half a lesson. EEVEE particle frames take about 4 s each at full size on an M1 with 8 GB (about 2 minutes per second of song), so the quick test is a draft (a 4 s test took 87 s), and the progress bar follows the frame range the script reports. `scripts/verify_dashboard_piano_visual.py` checks storing the look, the Send command, the render commands for both looks, the reported frame range and that guitar songs are unaffected. It then runs in background Blender to send a song into `piano-visual.blend`, checking the audio offset, that a failed send restores the previous lesson, that the lesson look asks for `piano-vertical.blend`, and that nothing is saved.

## 37. PIANO_VISUAL Shows Rising Musical Notes By Default, Plumes As An Option

Decision: The PIANO_VISUAL stage has two effects: `notes` (default) and `plumes` (decision 35). With notes, each key press sends up one glowing, upright note symbol (`guitar_video_app/integrations/piano_visual_notes.py`). The symbol follows the note's written length in beats from the prepared lesson: at least 1.5 beats is a hollow half note, at least 0.75 a quarter note, and anything shorter an eighth note with a flag. There are no beams, and the length is read by note id, so the JSON format is unchanged. A note appears 3 cm above its key with a short pop, rises about 0.2 m/s with a gentle sway and a small offset across the key, and lives 2.4 s plus how long it sounds (at most 2 s more). Its glow is full while the key is held, 75% while only the sustain pedal holds it and 55% after that, with a flash at birth. It fades over the last 40% of its life and cools from light to deeper blue. In final renders a soft round halo sits behind each symbol; it is left out of the viewport (Geometry Nodes "Is Viewport"), where Solid view cannot show its painted falloff and draws it as a flat square over the note. A faint trail of about 50 sparkles per second falls from where the note was, each fading in 0.8 s. Like the plumes, everything is computed from the scene time in the same Geometry Nodes object (`PianoVisual_Plumes`, one point per note with `pv_kind` 0/1/2). The three symbols are small flat meshes built by code as hidden template objects in the effect's collection. They are instanced turned to the active camera with their up axis on the camera's up, so they stand straight in the picture from any camera. `piano_visual_particles.install(data, effect='notes'|'plumes')` stores the effect on the scene (`pv_effect`), so reopening the `.blend` rebuilds the same effect, and the frame range ends when the last note and its sparkles have faded. The dashboard's Piano look has three choices: Lesson keys, Musical notes (`piano_look = 'visual'`, so songs already on the particle stage get notes) and Blue plumes (`'plumes'`). Send adds `piano_effect` to the `dashboard_sync` command, a failed send restores the previous lesson and effect, and renders pass `--effect` to `scripts/render_piano_visual.py` (default `notes`).

Rationale: In the viewport and at small sizes the plumes read as blue squares rather than music, while a note symbol says "this key just played" at a glance and its shape tells long notes from short ones. One symbol per key press keeps the picture readable in fast passages, where per-particle plumes merged into one cloud. Building symbols from code keeps the stage free of imported assets, and the notes are much lighter than the plumes: about 300 polygons at the busiest moment of the test phrase and under 900 in the 12 s demo, against 1,400 plume particles. Frames evaluate in under 10 ms, and an 8 s half-size draft rendered in about 3 minutes on an M1 with 8 GB, about the same as the plumes. `scripts/verify_piano_visual_notes.py` checks the symbol per written length, one note per key press (two for a repeated key), rise and fade timing, the pedal-held glow ratio, that notes face the camera upright, the sparkle count and fade, deterministic seeking, key and pedal motion, the polygon budget, switching to plumes and back, rebuilding on reload, and that the asset and the `.blend` on disk are unchanged. `scripts/verify_piano_visual_particles.py` now installs the plumes explicitly and gives the same results as before.

## 38. PIANO_VISUAL Notes And Plumes Have Colour Themes, Or Follow The Hand

Decision: The PIANO_VISUAL effects (notes or plumes) take a colour setting: `blue` (default, unchanged), `white`, `gold` or `hands`. With `hands`, right-hand notes are orange and left-hand notes blue, like the lesson piano's key colours (decision 32), and notes whose hand is unknown are white. The hand comes from the piano view (MIDI tracks, the hand planner or the dashboard's clicks), so nothing new is analysed. A palette is a deep, a main and a pale colour plus a key glow colour (`piano_visual_particles.PALETTES`). Each note's event point stores its palette as `pv_deep`, `pv_main` and `pv_pale`, and the glow material blends them by `pv_heat` exactly as the blue colour ramp did, so sparkles, halos, symbols and plumes all follow the note's colour, and the Blue theme renders the same as before. A key glows in the palette of the hand pressing it, or of the note the pedal is holding. The sustain pedal and Solid view use the theme's neutral colour. `install(data, effect, colors)` stores the choice on the scene (`pv_colors`) for reloads. The dashboard stores it per song (`piano_colors` column; NULL is blue; `POST /api/songs/<id>/piano-colors`, which raises the revision). A Note colour choice appears under Piano look when a piano song uses Musical notes or Particle plumes, and the second stage choice is renamed from Blue plumes to Particle plumes because plumes can now be any colour. Send adds `piano_colors` to `dashboard_sync`, a failed send restores the previous colours, and renders pass `--colors` to `scripts/render_piano_visual.py`. Black was left out because it would disappear on the dark stage.

Rationale: Colouring by hand shows who plays what, which is the point of a piano lesson, and matching the lesson piano's orange and blue keeps both looks consistent. Orange and blue also stay distinct for most colour-blind viewers. White and gold give non-lesson videos a different mood without new assets or render cost. Palettes on the points instead of per-theme materials let one material show both hands in the same frame. `scripts/verify_piano_visual_notes.py` checks that by hand a right-hand note and its key glow are orange and a left-hand chord and its keys blue, that a pedal-held key keeps its hand's colour, that the gold theme colours notes and pedal, and that blue is the default. `scripts/verify_dashboard_piano_visual.py` checks storing, sending and rendering the colours and restoring them after a failed send. A render of the Blue theme matches the previous code to within 1/255.

## 39. PIANO_VISUAL Camera Shots Are A Bar-Based Shot List, Planned In Python

Decision: A PIANO_VISUAL song can have a camera shot list (`camera_shots` column; NULL keeps the single presentation camera, unchanged). A shot starts on a bar (1-based) and has a camera, a move and a transition. There are six cameras. `wide` is the presentation camera's own view. The others are framed for a 9:16 short: `hero` (front left, 2.75 octaves), `along` (low along the keys, 3 octaves), `high` (from above, 2 octaves), `close` (just over an octave) and `side` (from the treble end). The moves are `static`, `push` (moves in 10% over the shot), `drift` (follows the music) and `arc` (swings 12°). A cut happens on the bar's downbeat frame; `blend` instead orbits from the previous shot, starting on the downbeat. A blend moves the look-at point in a straight line, turns the view the short way round the keys, and changes distance in proportion rather than by a fixed amount, so the camera stays on a curve around the keys instead of cutting across them. A blend lasts 0.75 s plus 1 s per 40° of turn and about 0.8 s per doubling of distance or lens. It is capped at 2 s, one bar and half the new shot. Blends, pushes and arcs use smootherstep easing, so speed and acceleration start and end at zero. `guitar_video_app/instruments/piano/camera.py` plans everything without Blender: bar times from the lesson's tempo map, which keys sound and when, the focus each shot follows and the camera at any second (`CameraPath.camera_at`). The focus looks 1.5 s ahead, ignores moves within a quarter octave and has a limited speed and acceleration. Each shot widens to fit the notes it must show, and its distance is solved so that the sounding keys and 0.40 m of rising notes stay inside the 9:16 safe area (4% from the left, 14% from the right for the platform buttons, 20% from the bottom for captions, 8% from the top). Auto (`auto_shots`) suggests a list from the music: shots of 3 to 10 s, at least 2 bars, about 6 s; cuts on big register jumps; a hero or wide opening that pushes in; hero or wide for dense or wide passages, close, along or high for sparse ones; no camera twice in a row; side only for sparse, narrow passages at most every 30 s; and a wide ending. Auto blends only between views at most 25° apart (wide, hero and close) whose focus moves less than half an octave, and it blends into the ending when the views are that close. Every other change is a cut. A first version blended in a straight line over a fixed 0.75 s with smoothstep easing. Big angle changes then swept fast across the keys (up to 4.4 m/s, with sudden jolts at the start and end of each blend) and felt rough. `integrations/piano_visual_camera.py` adds a separate `PianoVisual_ShotCamera` in a `PIANO_VISUAL_CAMERAS` collection, parented to the keyboard frame. A frame handler places it from the plan on every frame, with no keys, and makes it the scene camera. The list is stored in a text block (`PianoVisual_Camera_JSON`) so a reopened `.blend` rebuilds it. Removing the list deletes all of these and makes the presentation camera active again, untouched. `piano_visual_particles.install(..., camera=)` checks the list before changing the scene. The dashboard shows a Camera section (Wide or Shots) and, under the piano roll, a strip with one cell per bar for the whole song, coloured by camera. Click a bar, or shift-click or drag to pick several, then choose a camera (preset thumbnails in `ui/cameras/*.png`, rendered by `scripts/make_camera_previews.py`), a move or a transition, which apply to those bars. Neighbouring bars with the same camera and move join into one shot, and Whole shot selects every bar of a shot. A new shot begins with a cut; a shot whose first bars are given to another camera keeps its transition. Test 4 s starts at the first selected bar. The strip replaced a first version: a lane that only showed the piano roll's two bars at a time, with draggable shot edges and Split and Delete buttons, which made it hard to control the camera bar by bar. The API is `GET`, `PUT` and `DELETE /api/songs/<id>/camera` and `POST /api/songs/<id>/camera/auto`; saving raises the revision only when the list changes. Send adds `camera_shots` to `dashboard_sync`, and a failed send restores the previous list. A successful piano Send also sets the scene's playback to Sync to Audio. Before, the scene played every frame, so when the viewport could not draw 60 fps, playback slowed down unevenly and drifted from the WAV. Now the viewport skips frames to keep time with the WAV. Renders are unaffected. Renders write `camera_shots.json` beside `piano_view.json` and pass `--camera` to `scripts/render_piano_visual.py`.

Rationale: Viewers of a vertical short need to see the keys being played and the notes rising from them, which one wide view of 88 keys shows small. Shots tied to bars cut with the music and stay valid when the audio offset or FPS changes, and keeping the shot list separate leaves the piano view format and the presentation camera as they were. Planning in Python keeps musical decisions out of Blender. It also makes every frame a pure function of time, so any frame renders the same in any order and nothing is baked. Shots without keys keep the `.blend` free of test animation. Solving each shot's distance from the notes it must show, rather than fixed framings, keeps playing keys out of the platform UI areas. Auto gives a sensible starting list that the user edits, rather than a black box. `scripts/verify_piano_camera.py` checks Auto (determinism, opening and ending, no repeats, shot lengths, side spacing, a cut at a register jump), that every sounding key stays in the safe area for every camera and move, cuts on downbeat frames, focus speed and look-ahead, blend length, speed and acceleration with smooth starts and ends, and that bad lists are refused. `scripts/verify_piano_visual_camera.py` checks the same in Blender with `world_to_camera_view`, plus seeking, reload, notes facing the shot camera, cleanup and that the presentation camera and `.blend` are unchanged. `scripts/verify_dashboard_piano_visual.py` checks the API, Send, renders from a shot's bar and restoring after a failed send.
